## Local Setup

### Prerequisites

- **Docker** and **Docker Compose** (v2)
- **Ollama** installed natively: `curl -fsSL https://ollama.com/install.sh | sh`
- **Git**

### First-time setup

```bash
# 1. Clone
git clone <repo-url>
cd Talvyn

# 2. Copy environment templates
cp .env.example .env
cp frontend/.env.local.example frontend/.env.local

# 3. Set secrets in frontend/.env.local
#    Generate with: openssl rand -base64 32
NEXTAUTH_SECRET=<generate>
INTERNAL_API_SECRET=<generate-32-chars>   # must match backend

# 4. Set the same INTERNAL_API_SECRET in backend/.env
INTERNAL_API_SECRET=<same-value-as-above>

# 5. Start everything
./start.sh
```

`./start.sh` auto-detects your hardware, writes `backend/.env.hardware`, starts Ollama natively, pulls the right model, and brings up all Docker services.

On first startup the frontend seeds the default admin account automatically
(`frontend/prisma/seed.ts`):

- Email: `acmeai@talvyn.com`, or `SEED_ADMIN_EMAIL` if set
- Password: `SEED_ADMIN_PASSWORD` if set in `frontend/.env.local`; otherwise a
  random password is generated and printed once to the frontend container
  logs (`docker compose logs frontend | grep seed`)

**Normal access is via Nginx on port 80 (`http://localhost`).** Direct ports 3003 (frontend) and 9000 (backend) are available for debugging.

### Rebuilding after package changes

If you add Python packages to `requirements.txt`, you must rebuild the backend and worker images:

```bash
docker compose build backend worker
docker compose up -d backend worker
```

### Re-starting

```bash
./start.sh    # idempotent — safe to run again if already running
./stop.sh     # graceful shutdown
```

### Checking logs

```bash
docker logs talvyn_backend  -f
docker logs talvyn_worker   -f    # ARQ job runner (Ollama work happens here)
docker logs talvyn_frontend -f
docker logs talvyn_nginx    -f
# Ollama logs
tail -f /tmp/ollama.log
```

## Backend — FastAPI

### Request flow

```text
Browser / Next.js  →  /api/proxy/[...path]  →  FastAPI  →  Service  →  DB / Redis
                                                    │
                                              ARQ enqueue
                                                    │
                                             ARQ Worker  →  Ollama  →  DB
```

All admin API calls from the browser go through the Next.js proxy at `/api/proxy/`. The proxy adds `X-Internal-Token` and forwards to FastAPI. Ollama-heavy work is enqueued to ARQ and never blocks a request handler.

Candidate test-taking calls go through the public Next.js candidate proxy at `/api/candidate/`. It only forwards allowlisted attempt endpoints and passes the raw magic-link token as `X-Attempt-Token` where required. Public assessment-link registration goes through `/api/public/`, which only forwards the public-link resolve/register endpoints.

SSE progress streams (`/api/v1/tests/progress/{jd_id}/stream`) are handled by the proxy using native `fetch()` + `ReadableStream` pipe-through (not axios) to avoid response buffering.

### Adding a new endpoint

1. Add the route handler to the relevant file in `backend/app/api/v1/`.
2. Add request/response Pydantic schemas to `backend/app/schemas/`.
3. Add business logic to a service file in `backend/app/services/`.
4. If the new endpoint triggers Ollama work, add a task wrapper to `backend/app/worker.py` and enqueue via `arq_pool`.

### Schema migration workflow

```bash
# 1. Edit the ORM model in backend/app/db/models/
# 2. Generate a migration
docker exec talvyn_backend alembic revision --autogenerate -m "add_column_x"
# 3. Apply it
docker exec talvyn_backend alembic upgrade head
# 4. Restart backend (migrations run automatically via prestart.sh on restart)
docker compose restart backend
# 5. If the changed table is also in Prisma schema, update schema.prisma and regenerate:
docker exec talvyn_frontend npx prisma generate
```

## Frontend — Next.js

### Page routing

All admin pages live under `src/app/(admin)/dashboard/`. The `(admin)` route group applies the admin layout (sidebar, auth guard).

Candidate test pages live under `src/app/tests/[token]/` (with legacy `/test/[token]` still present) and use a completely separate layout with no sidebar. Public assessment registration lives under `src/app/apply/[slug]/`.

### Server vs client components

- **Server components** (no `"use client"`) — use `serverFetch.ts` for data fetching. Benefit from Next.js ISR caching (`revalidate: 30`).
- **Client components** (have `"use client"`) — use `apiClient` (axios via `/api/proxy/`). Used for interactive pages.

### SSE in client components

Use native `EventSource` pointing to `/api/proxy/api/v1/tests/progress/{jdId}/stream`. The proxy detects the `/stream` suffix and pipes the upstream `ReadableStream` directly. Never use axios for SSE paths — it buffers the entire response.

### API client

Two paths:

- `src/lib/api/client.ts` → `apiClient` — axios instance, client-side only, routes through `/api/proxy/`
- `src/lib/serverFetch.ts` → `serverFetch()` — native `fetch()`, server-side only, calls FastAPI directly with `X-Internal-Token`; enables Next.js ISR caching

### Bulk invite (CSV)

CSV parsing is client-side in `BulkInviteForm.tsx`. The parsed list is sent as a JSON body to `POST /api/v1/invitations/bulk`. No multipart upload — avoids all proxy-level binary encoding issues.

### Admin seeding

`frontend/scripts/start-dev.sh` runs inside the container before Next.js starts:

```bash
npx prisma db seed   # creates acmeai@Talvyn.com if not exists
npm run dev
```

The seed is idempotent — skips users that already exist, so manual password changes are preserved across restarts.

## Database

Both the backend (SQLAlchemy) and frontend (Prisma) connect to the same PostgreSQL instance.

- **Backend** owns all schema changes via Alembic migrations.
- **Frontend** reads `frontend/prisma/schema.prisma` for type generation — must stay in sync with the Alembic-managed schema.
- **Single source of truth:** Alembic.

### Key tables

| Table | Purpose | Notes |
| --- | --- | --- |
| `users` | Admin accounts | bcrypt-hashed passwords; seeded on startup |
| `job_descriptions` | JD uploads | `parse_status` + `generation_status` columns |
| `jd_extracted_data` | AI-extracted skills | JSON arrays for skills/topics/seniority |
| `tests` | Generated tests | 3 per JD (TECHNICAL, REASONING, PROBLEM_SOLVING) |
| `questions` | Questions per test | MCQ options stored as JSON |
| `candidates` | Candidate records | email-based identity |
| `invitations` | Candidate invitations | HMAC token stored as hash; invited_by FK → users; `TERMINATED` status + `integrity_violation_reason`/`terminated_at` on integrity violation |
| `test_attempts` | Per-candidate attempt | status: NOT_STARTED → IN_PROGRESS → SUBMITTED → EVALUATED, or → TERMINATED (terminal, candidate-side integrity violation) |
| `candidate_answers` | Per-question answers | upserted via `ON CONFLICT` on autosave |
| `evaluations` | AI evaluation result | per attempt; has admin override fields; `embedding vector(768)` nullable, opt-in; `overall_ai_likeness_percentage`/`overall_ai_detection_confidence`/`flagged_answer_count` nullable, opt-in (`AI_LIKENESS_ENABLED`) |
| `question_feedback` | Per-question AI feedback | includes `admin_awarded_score`; `estimated_ai_percentage`/`ai_detection_confidence`/`suspicious_phrases`/`ai_detection_explanation`/`ai_detection_recommendation` nullable, opt-in, open-ended only |
| `suspicious_events` | Tab-switch / copy events | logged during test; on a hard violation the row is tagged `led_to_termination: true` in `event_metadata` |

### Exam integrity enforcement

`POST /api/v1/attempts/{id}/terminate` (`attempt_service.terminate_attempt`) is
the single enforcement chokepoint: it sets `TERMINATED` on both the attempt
and its parent invitation in one transaction, so blocking every remaining
test in a multi-test invitation just falls out of the existing
invitation-level check in `start_attempt` — no per-test bookkeeping needed.
It's idempotent (retried calls return the existing terminal state) and always
inserts a `SuspiciousEvent` row, so the audit trail and the enforcement
action can never disagree.

The frontend hook `useSuspiciousEvents` (`frontend/src/hooks/`) owns both the
hard-termination triggers (`visibilitychange`/`blur` → calls `onViolation`)
and the soft blocking (copy/cut/paste/contextmenu/keyboard → calls
`onBlocked` for a toast); the exam page (`frontend/src/app/test/[token]/exam/page.tsx`)
wires both callbacks and locks the UI client-side immediately on violation,
before the network round-trip to `/terminate` completes.

This is a deterrent, not unbypassable protection — never represent it as
foolproof in code comments, UI copy, or docs.

### PL/pgSQL stored function

`calculate_evaluation_scores(p_attempt_id UUID)` — aggregates MCQ, open-ended, and code scores from `question_feedback` and returns a full breakdown. Installed via Alembic migration `d9e8f7a6b5c4`. Available via `GET /api/v1/evaluation/{attempt_id}/verify-scores`.

### pgvector (opt-in)

Postgres image is `pgvector/pgvector:pg16`. Migration `db7cdbbfd2a8` adds `CREATE EXTENSION IF NOT EXISTS vector`, a nullable `evaluations.embedding vector(768)` column, and an HNSW cosine index. Disabled by default — see `EMBEDDING_ENABLED` above. `backend/app/db/models/_types.py:VectorType` falls back to a JSON column on SQLite so the test suite doesn't need the extension.

## AI / Ollama

Ollama runs **natively on the host** (not inside Docker) to get full GPU/CUDA access. The backend and worker containers reach it via `host.docker.internal:11434`.

### Model selection

`./start.sh` picks the model automatically based on detected GPU VRAM. **Never set `OLLAMA_MODEL` in docker-compose.yml `environment:` block** — it overrides `env_file:` values and defeats auto-detection.

### Evaluation pipeline

```text
Candidate submits → enqueue evaluation (or admin triggers manually)
    → MCQ auto-scored (shuffle-aware exact match)
    → OE questions sent to Ollama in parallel (asyncio.gather)
    → per-question feedback stored → aggregate Ollama call → report ready
    → Admin can verify scores via PL/pgSQL function
```

## Authentication

### Admin (NextAuth + bcrypt)

- Credentials provider: email + bcrypt password
- JWT strategy — no DB lookup on session reads (`getToken()` only does HMAC verify)
- Session stored in an httpOnly cookie, 8-hour expiry
- Nginx Lua script checks cookie structure on all `/api/v1/` paths
- All admin routes protected by `middleware.ts`

### Candidates (magic links + HMAC)

- No account needed — candidates get a one-time link by email
- Token is a random UUID signed with HMAC-SHA256 using `MAGIC_LINK_SECRET`
- Only the **hash** is stored in the DB — raw token never touches storage
- Link opens `/tests/[token]` — validates token, starts or resumes the attempt through `/api/candidate`
- Token expires after 72 hours; resending a new invitation rotates the token (old link dies)
- Public assessment links open `/apply/[slug]`; after the candidate enters their details, the backend mints a unique private `/tests/[token]` invitation.

## Key Architectural Decisions

**Why Nginx/OpenResty at the front door**
OpenResty embeds LuaJIT. The `jwt_check.lua` script does a structural JWT check (<1ms) before any Python process is involved. Full HMAC verification still happens in FastAPI.

**Why SSE uses native fetch (not axios) in the proxy**
Axios buffers the entire response before returning — SSE events would never arrive until the stream closes. The proxy switches to native `fetch()` + `ReadableStream` pipe-through when the path ends in `/stream`.

**Why Redis for progress tracking**
4 uvicorn workers are separate OS processes. A `/tmp` file written by worker #2 is invisible to worker #3. Redis is a single shared store visible to all workers and the ARQ process.

**Why ARQ for Ollama jobs**
FastAPI `BackgroundTasks` share the event loop with request handlers. A 15-minute Ollama job holds a uvicorn worker slot. ARQ isolates all Ollama work to a dedicated process.

**Why the WASM parser keeps a server-side fallback**
Client-side PDF/DOCX extraction can fail (corrupt files, scanned PDFs, WASM load failure). `POST /jd/upload` treats a missing/empty `extracted_text` field as "parse it server-side the normal way" rather than an error — the original file is uploaded and stored either way, only the CPU-bound parse step is skipped when the browser already produced usable text.

**Why pgvector embeddings are opt-in**
`EMBEDDING_ENABLED` defaults to `false` because it requires pulling an extra Ollama model (`nomic-embed-text`) that low-VRAM hardware profiles may not want. `embedding_service.generate_embedding()` never raises — every failure (disabled, model missing, Ollama down) returns `None` and leaves `embedding` as `NULL`, so the evaluation pipeline never depends on it succeeding.

**Why the AI-likeness estimate is opt-in and never fails evaluation**
`AI_LIKENESS_ENABLED` defaults to `false` — LLM-based AI-text detection is unreliable in both directions, so it must be a deliberate admin choice, not a silent default. `ai_detection_service.estimate_ai_likeness()` mirrors `generate_embedding()`'s contract exactly: every failure (disabled, empty answer, Ollama down, malformed response after retries) returns `None` rather than raising, leaving the new `question_feedback`/`evaluations` columns `NULL`. This is a probabilistic writing-style signal, never a verdict — every layer of the UI says so explicitly, and it must never be presented otherwise.

**Why `job_timeout` is computed, not hardcoded**
`ollama_timeout_seconds` is the per-request timeout. The full generation job covers 3 tests × up to 4 Ollama calls each. The job timeout is `ollama_timeout_seconds × (1 + max_retries) × 3 + 120s`.

**Why Ollama runs natively (not in Docker)**
Consumer GPUs require direct CUDA access. Docker GPU passthrough on Ubuntu conflicts with native driver setups.

**Why sequential test generation (not parallel)**
With `OLLAMA_NUM_PARALLEL=1` (required for ≤4 GB VRAM), the 2nd and 3rd parallel coroutines wait 150s+ in Ollama's queue before starting, burning timeout budget. Sequential calls ensure each completes within its own timeout.

**Why both Prisma and SQLAlchemy**
Prisma is in the frontend for type-safe DB access in Next.js server components. SQLAlchemy is in the backend for full async support, Alembic migrations, and complex queries. Alembic owns all schema changes.

**Why the Next.js proxy pattern**
`INTERNAL_API_SECRET` must never reach the browser. The Next.js API route at `/api/proxy/` runs server-side, injects the secret header, and forwards to FastAPI.

**Why bcryptjs in the frontend (not backend)**
Admin password verification happens in NextAuth's `authorize()` callback — a Next.js server function. Using `bcryptjs` (JS) avoids a round-trip to the Python backend on every login.
